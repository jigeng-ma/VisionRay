# Android APP 与 AI 眼镜自动化测试框架规划

当前状态：基础框架及中文窗口已实现；2026-09-11 接入 G 系列配对用例并完成 G1 实机验证。以下为原始规划，实际目录与 JSON 配置格式以根目录使用说明及 G系列配对自动化.md 为准。

## 一、已确认需求

- 第一阶段支持 Android，驱动层预留后续 iOS 扩展。
- 当前有四款产品，每款包含 1～3 个型号。
- APP 大部分功能共用，部分功能、页面元素、操作流程存在产品或型号差异。
- 眼镜没有 SDK，测试涉及配对、拍照、录像、语音、触控和固件升级等操作。
- 第一阶段单部手机配合一副眼镜执行，不需要多设备并行。
- 手机与眼镜均可更换，每轮由使用者选择手机、测试产品型号及眼镜名称信息；设备序列号不写死在业务用例中。
- 提供可视化窗口，动态读取 Excel 全部 Sheet 名称作为模块列表，只执行勾选模块对应的用例。
- 用例规模为几千条，支持按功能模块筛选执行和统计。
- Excel 有固定用例编号列，每个执行轮次输出独立文件，具体格式后续提供。
- 沟通及项目文档使用中文；被测 APP 优先使用英文界面。页面文案断言按界面语言配置，预留其他语言扩展。
- Excel 原有表头与用例文字保持原样。代码标识符、文件路径和技术状态码可使用英文，不代表要求 APP 以外的内容全部使用英文。

## 二、整体架构

初步采用 Python + pytest 编写和执行测试，Android 通过 Appium 适配器操作，YAML 管理配置，SQLite 持久化执行结果。收到 Excel 样例后实现对应回填适配器。依赖版本在实现阶段确认并锁定。

业务用例调用公共流程和页面对象。公共流程协调手机端操作与眼镜动作，产品差异通过配置和专属流程实现管理，避免在每条用例中重复判断产品名称。

```text
执行入口：选择产品、型号、模块、用例集
    ↓
用例元数据校验与适用性判断
    ↓
业务用例与公共业务流程
    ↓
页面对象与可复用组件
    ↓
Android 驱动与眼镜动作适配器

分层配置 → 各业务层
执行事件 → SQLite → 模块统计与 Excel 回填
失败证据 → 各轮次独立目录
```

## 四、产品及型号配置

配置按“公共 → 产品 → 型号”顺序覆盖。字典递归合并，列表和单值整体替换。连接设备前检查未知字段、必填值和产品型号组合是否合法。运行清单记录最终生效配置及其摘要，不保存账号密码等凭据。

产品能力采用“支持、不支持、未知”三种状态。不支持的功能记录为不适用；能力未知时阻塞相关用例并提示补齐配置。产品信息未提供前，可以建立明确标记的占位配置，但禁止用于真实执行。

功能能力、页面配置、流程差异和产品预期值分别维护。APP 和固件版本先作为执行信息记录，确认存在版本差异后再引入版本覆盖，避免无依据地增加配置复杂度。

## 五、元素维护与语言

元素使用语义名称，例如 `device.home.capture_button`。优先通过稳定的资源 ID、无障碍标识定位，选择器限定在对应页面或组件范围。要求匹配唯一元素并等待明确状态，不默认点击首个匹配项，也不以坐标作为常规定位方式。

页面对象负责元素定位及交互，公共流程负责业务步骤，断言验证实际可观察结果。点击成功本身不等于拍照、同步或升级成功。

被测 APP 优先设置为英文界面，并记录实际界面语言。需要按文本定位或断言时，从语言配置读取英文文案，不在大量用例中直接写死。产品页面差异与界面语言分别配置。

提供按页面执行的元素检查入口，检查配置语法、元素唯一性、可见性，并为失败项留存截图。实际定位规则及导航流程必须在获得 APP 和设备后验证。

## 六、用例组织与规模管理

每条可执行用例包含唯一且稳定的用例编号、功能模块、优先级、所需能力和执行模式。编号与 Excel 对应。参数化场景必须明确映射到独立编号，或事先约定汇总规则，不能让多个结果无提示地覆盖同一行。

收集用例时先检查重复编号和元数据缺失，再初始化设备。支持按产品、型号、模块、优先级、编号及用例集筛选。业务逻辑使用 Python，YAML 仅负责配置和数据。

用例不依赖上一条用例成功。通过可复用的前置与清理机制建立状态；共享耗时准备步骤时，每条用例仍须验证自己的起始状态。固件升级划入独立用例集，并显式配置目标固件。

## 七、眼镜实体操作边界

眼镜动作接口覆盖实体按键、触控、音频刺激、开关机等操作。只有 APP 实际提供入口的动作，才能通过手机端触发。

没有 SDK 或工装时，部分动作无法全自动完成。可预留人工辅助适配器，但仅在明确选择辅助执行模式时启用。无人值守模式遇到无法触发的必要动作，应记录为阻塞并给出原因，不能无限等待或默认成功。

场景分为全自动、人工辅助和暂无法执行三类。人工完成步骤时记录确认信息，随后仍需验证可观察结果。是否接受人工辅助执行，尚待确认。

## 八、执行稳定性

执行前检查手机身份、APP 安装及版本、权限和可用连接。眼镜身份、固件、电量和状态仅通过 APP 或已有可用接口实际读取，无法读取时明确记录，不能假定检查通过。

为当前手机与眼镜组合设置本地资源锁，避免误启动多个任务争用设备。逐条、逐次持久化执行记录，采集时间、错误类别、截图及可用日志。证据采集失败不得覆盖原始错误。

不统一自动重试所有失败。仅对已配置的可恢复问题重试，保留每次尝试，单独标识重试后通过。中断时保存已完成结果，将正在执行的尝试标记为中断。续跑前重新建立设备状态，并记录与原执行轮次的关系。

## 九、结果状态及模块统计

| 状态码 | 中文含义 | 判定说明 |
|---|---|---|
| PASS | 通过 | 断言验证成功 |
| FAIL | 失败 | 断言不符合预期 |
| ERROR | 执行异常 | 执行过程发生非预期异常 |
| BLOCKED | 阻塞 | 必要前置条件或操作能力不可用 |
| SKIPPED | 跳过 | 因明确规则主动跳过 |
| NOT_APPLICABLE | 不适用 | 产品或型号不支持所需功能 |
| INTERRUPTED | 中断 | 执行过程中被中断 |
| NOT_RUN | 未执行 | 已选中但尚未执行 |

按产品、型号和模块统计各状态数量。断言通过率定义为 `PASS / (PASS + FAIL)`，分母为零时显示“不适用”。同时展示异常、阻塞数量及执行覆盖情况，避免单一通过率掩盖未完成测试；重试后通过单独标记。

每轮记录执行编号、产品型号、手机身份、可观察的 APP 和固件版本、界面语言、选中模块与用例、时间、配置摘要，以及可获取的框架代码版本。

## 十、Excel 回填约定

收到样例后确定 Sheet、表头行、固定编号列及结果列，通过配置映射，不假定表头为英文，也不依赖固定行号。

用例编号按文本匹配，保留前导零。回填前检查重复编号、缺失编号、映射歧义和不支持的工作簿特性。未经明确规则，不做可能改变编号含义的转换。

每轮使用唯一执行编号和独立目录，从模板生成新的结果文件，不修改源模板，不覆盖其他轮次。仅初始化已约定的本轮结果区域，避免历史结果残留为当前结果；可编辑列在收到样例后确定。

先写入目标目录中的临时文件，验证后再重命名为正式文件。文件占用或导出失败时，数据库保留执行结果，支持后续重新回填。格式、公式、宏和嵌入对象的保留能力需结合真实模板验证。

## 十一、实施与验收顺序

1. 基础能力：配置结构、三级继承、用例元数据、筛选、状态模型及结果持久化；验证配置覆盖、编号校验、筛选和异常中断时的数据保留。
2. Android 接入：驱动生命周期、页面对象、元素检查、前置检查、清理及失败取证；使用实际 APK 和一组设备验证。
3. 产品适配：录入真实产品型号配置，在代表性硬件上验证公共流程及差异流程。
4. 报告回填：实现模块统计及真实 Excel 模板适配；验证行排序、前导零编号、重复和未知编号、多轮独立文件、中断结果及格式保留。
5. 小范围试运行：覆盖公共功能、UI 差异、不支持的能力、实体操作不可用、断言失败和结果回填。这些是框架验收场景，不是开始批量编写业务用例。
6. 批量扩展：框架试运行通过后制定用例编写规范，按模块逐步编写业务用例。

## 十二、后续所需信息

- Excel 样例及目标结果列，可在回填阶段提供。
- 产品、型号的真实名称及能力差异。
- 测试 APK、启动信息或获取方式、Android 连接信息，以及需要时的测试账号。
- APP 是否包含 WebView 页面。
- 是否接受人工辅助实体操作，以及现有实体控制、音频播放等设备情况。

以上信息不阻碍先实现配置和结果存储基础能力，但真实设备执行、完整硬件自动化以及 Excel 模板兼容性需要相应输入才能验证。

## 十三、可视化窗口与每轮设备选择

窗口操作顺序：选择 Excel → 勾选 Sheet 模块 → 选择手机 → 选择产品及型号 → 选择眼镜设备并确认名称 → 执行前检查 → 开始执行 → 查看模块结果与导出文件。

### 模块选择

- 读取所选 Excel 中全部 Sheet 名称，提供多选、全选和取消全选。
- Sheet 是功能模块来源；仅执行被选 Sheet 的用例编号对应的自动化实现。
- 更换 Excel 后重新读取模块并校验选择，不沿用旧文件的模块状态。
- 未关联自动化实现的编号明确提示，不计为通过。Sheet 与用例编号联合定位回填位置，具体映射待样例确认。

### 设备与型号选择

| 窗口字段 | 来源及用途 |
|---|---|
| 手机 | 扫描已连接的 ADB 设备，展示型号、序列号、Android 版本和授权状态，由使用者选择 |
| 产品 | 从已维护的产品配置选择 |
| 测试型号 | 随产品联动筛选，决定功能能力、页面元素及流程差异 |
| 眼镜设备 | 从已连接的 ADB 设备选择，以序列号作为本轮命令目标 |
| 眼镜名称 | 支持选择已有名称或手动录入；可读取的系统名称仅作建议值，与实际蓝牙或 APP 显示名称分别记录 |

设备名称、业务型号与 ADB 序列号分别存储。系统上报型号不能自动替代业务型号；同名眼镜通过序列号区分。设备角色由使用者确认，不能依据设备排列顺序推断。当前已检查的手机和眼镜仅作为检查样例，不作为固定执行目标。

### 刷新、校验和执行绑定

- 提供“刷新设备”按钮；设备未授权或离线时显示原因并禁止作为执行目标。
- 扫描刷新后重新检查原选择是否仍有效。可记住上次选择作为便利默认值，但每轮开始前必须重新验证其在线状态。
- 手机与眼镜不能选择同一个序列号。检查手机安装了目标 APP；核对已配置的产品型号约束，不推断未知的产品归属。
- 名称用于显示和记录，ADB 序列号用于控制；APP 内的连接状态和连接对象另行验证，USB 接入本身不等于配对完成。
- 点击开始后固化本轮手机序列号、产品型号、眼镜序列号及名称，所有设备命令显式指定目标。运行中禁止编辑当前轮次的设备选择。
- 运行中设备断开时记录异常并停止向其发送后续业务动作。若允许恢复，仅重新连接并验证同一序列号；不得自动改用另一台设备。更换测试设备应结束当前轮次后新建一轮。
- 本轮结果清单及报告保存上述选择信息。Excel 中对应信息的展示位置待模板确定。
